# Plugin SDK and registration

WordPress allows extensions to declare content types and taxonomies, enrich content with fields and blocks, transform values through filters, add routes and admin navigation, and supply settings and translations. Atlas preserves these capabilities using site-local, plugin-owned registrations that publish after activation commits. Registration shapes are explicit and validated, and presentation labels refer to locale catalog keys. Consumers in later phases render the declarations. Actions, filters, events and service discovery remain distinct. Duplicate identifiers within a release fail activation. Cross-plugin service calls require a declared dependency and an active provider.

Routes occupy a plugin-owned path under the versioned API, with explicit access policy and Zod request and response contracts. Activation and deactivation change dispatch and OpenAPI without restarting the API. Validate input before calling a handler and validate/project outputs before returning them. Unauthorized users and requests for an inactive site/plugin binding cannot reach plugin handlers. Preserve registered schema and settings versions across supported upgrades. Settings edits are validated and version checked, and generate a UI schema without executing presentation code.

Database access offers bounded, parameterized operations on the release's migrated tables with site scope from the host. Upgrade callbacks use the lifecycle transaction for migrations and settings, and can fail the upgrade. Route responses should avoid exposing raw database rows or exception details. Mail, jobs, cache and storage use site and plugin scopes. Network access requires an approved HTTPS origin, public resolved addresses, pinned connections, redirects disabled and bounded responses. Jobs use ADR 0010 and carry versioned owner and site identity. Deny unsupported adapters or operations. Trusted modules still hold process authority, as ADR 0003 describes.

Tests cover staging, cleanup, validation, version compatibility, permission denial, schema generation and calls made through supported adapters.

Sources include the [hooks handbook](https://developer.wordpress.org/plugins/hooks/), [custom post types](https://developer.wordpress.org/plugins/post-types/registering-custom-post-types/), and [activation behavior](https://developer.wordpress.org/plugins/plugin-basics/activation-deactivation-hooks/).
